### P3-vs-P4 tension — surfaced honestly (user decision point)
The mandate literally says "per-board VE cross-board." P3 (derived rollup) **structurally cannot do cross-board**: `epic_id` is a same-board self-FK (core.py:320), so an epic — and any rollup over epics — is board-bound. Cross-board therefore *forces* P4 (a new milestone entity, board_id NULL). So round-1 with P3-only **consciously leaves the cross-board half of Theme B unmet.** Why I still defer P4:
- The immediate, concretely-stated pain is per-board epic progress ("epicler ilerliyor ama göremiyoruz") — P3 fully answers it, cheaply, with no migration.
- Cross-board is the second-order want, and today's active work lives on *separate* boards/projects (GameX, Lipsync, Flappy) with **no named cross-board milestone** on the table — it is aspirational, not pressing.
- P4 is a live-DB migration; running it *before* staging (P1) exists directly contradicts Theme A's hard safety constraint. The only safe ordering is P1 → (P3 now) → P4-after-staging.

**Decision the user owns:** if cross-board milestones are needed NOW, P4 is unavoidable — but accept that means a schema migration on the live tool before its own safety net exists (self-contradictory with Theme A). The safe, YAGNI-correct sequence is: ship P3 now for the visible per-board progress, stand up staging (P1/P2), then do P4 as staging's first customer once a real cross-board milestone is named.
