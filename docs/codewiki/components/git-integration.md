# Git Integration

> Local-first git readback layer (G1–G7): repository config, hardened reader, commit cache + WebSocket fan-out, read API, diff API, live refresh endpoint + background poller, host-side hook installer + CLI connect_repository for ops self-service.

## Current behavior

The git integration is split across five layers:

**G1 — Repository config** (`app/api/repositories.py`, `app/services/repositories.py`): REST endpoints and ORM (`Repository` model). **PH-221: 1 board : 0..N repos** (was 1:1) — exactly one repo per board is the **primary** (`is_primary=true`). Identity within a board is the stable **`slug`** (slugified, unique per board via `uq_repository_board_slug`); the partial unique index `uq_repository_one_primary` (`postgresql_where`/`sqlite_where` `is_primary`) + a service invariant enforce the one-primary rule. `Board.repositories` (uselist=True) + a `Board.primary_repository` property (back-compat accessor over the loaded collection; `board_response`/`BoardResponse.repository` now serialize the primary). FK `boards.id` ondelete=CASCADE; per-repo `git_commits`/`git_branches` cascade unchanged. Collection routes: `GET /repositories` (list, member), `POST /repositories` (add, admin — first repo auto-primary, slug deduped by `-2`/`-3` suffix), `DELETE /repositories/{id|slug}` (admin — auto-promotes the oldest remaining repo if the primary is removed), `POST /repositories/{id|slug}/set-primary` (admin — demote→flush→promote so the partial index never trips). The singular `PUT/DELETE /api/boards/{key}/repository` routes are KEPT as **primary-aliases** (PUT upserts the primary, DELETE removes it) so the un-migrated frontend keeps working until PH-224/225. All `/git/{status,graph,branches,commits,commits/{sha},commits/{sha}/diff,diff}` reads + `/git/refresh` gain an OPTIONAL `repo` query param (**slug or id**, id precedence on the rare collision) routed through the single resolver `services.repositories.resolve_repository`: omitted → primary (`409 RepoNotConfigured` if no primary), set → that repo (`404 NotFound("repository")` if unmatched). `git_queries._get_repo(session, board, selector=None)` and `git.sync.sync_repo(session, board, repo=None)` both default to primary; the background poller passes each `Repository` row explicitly so it syncs EVERY repo of EVERY board. Validates `local_path` starts with `/repos/` (allowlist enforced at the reader level). Provider values restricted to `github|gitlab|local` via CHECK constraint. (`RepositorySummary`/`RepositoryResponse` gained additive `slug`/`name`/`is_primary`; new `RepositoryCreate`/`RepositoryListResponse`.)

**G2 — Hardened reader** (`app/git/reader.py`): Read-only GitPython wrapper with five defense-in-depth layers (path allowlist via `realpath`, env hardening with `GIT_CONFIG_NOSYSTEM=1`+`GIT_CONFIG_GLOBAL=/dev/null`, per-call `-c` overrides disabling `core.fsmonitor`/`core.pager`/`protocol.file.allow`, `search_parent_directories=False`, no write calls). Public async wrappers (`aopen_repo`, `alist_branches`, `awalk_commits`, `acommit_files`) use `asyncio.to_thread` to avoid blocking the event loop. Returns typed dataclasses (`BranchInfo`, `CommitInfo`, `CommitFileChange`). **G5 adds**: `diff_text`/`range_diff` (sync) + `adiff_text`/`arange_diff` (async) for on-demand unified diff generation; new typed return shapes `FileDiff` (per-file patch entry) and `DiffResult` (aggregate with top-level `truncated` flag).

**G4 — Read API** (`app/api/repositories.py`, `app/services/git_queries.py`): Four cache-backed GET endpoints under `/api/boards/{key}/git/`: `graph` (DAG payload with limit + branch-filter; `GitGraphResponse` = commits[] + branches[] + tags[]), `branches` (all branches with ahead/behind vs. default; `GitBranchesListResponse`), `commits` (cursor-paginated by `before=<sha>` → committed_at filter; `GitCommitsListResponse`), `commits/{sha}` (full commit detail + per-file numstat; `GitCommitDetail`). All auth via `_require_board_member`; no Repository row → 409 `repo_not_configured`; empty cache → 200 empty arrays; short sha (≥7 chars) accepted in `commits/{sha}`, collision → 404. Service layer in `git_queries.py` (cache-only, no reader.py on request path). **PH-266: `graph.commits[]` is emitted in a deterministic TOPOLOGICAL order** — `graph_payload` fetches the full candidate set ordered `committed_at DESC, sha DESC` WITHOUT a DB LIMIT, runs `_topological_order(commits, default_head)` (Kahn, newest-first / child-before-parent over IN-WINDOW parent edges; the default-branch head sha is the PRIMARY ready-set ordering key so it lands at index 0 whenever it is a source — even when an open side-branch tip has a newer `committed_at`; remaining tie-break `(committed_at, sha)`), THEN truncates to `limit`. The legacy DESC-only order let a first parent sort ABOVE its child on a timestamp tie, which the FE lane layout rendered as a false "open/unmerged" ring (only `commits` is reordered; `branches[]` + ahead/behind logic are unchanged; `commits`/`commits/{sha}` paginated reads still serve plain `committed_at DESC, sha DESC`).

**G5 — Diff API** (`app/api/repositories.py`, `app/api/tickets.py`, `app/services/git_queries.py`, `app/git/reader.py`): Three new GET endpoints for on-demand patch text: (1) `GET /api/boards/{key}/git/commits/{sha}/diff?path&context` — single-commit diff against first parent (or empty tree for initial commit); live reader call; `DiffResponse{sha, files[], truncated}`. (2) `GET /api/boards/{key}/git/diff?base&head&path&context` — three-dot merge-base range diff (`base...head`); `RangeDiffResponse{base, head, files[], truncated}`. (3) `GET /api/tickets/{key}/commits` — cache-only list of commits linked to a ticket via `git_commit_tickets`; `TicketCommitsResponse{branch_name, branches[], commits[]}` with per-commit aggregated `additions`/`deletions`/`files_changed` from `git_commit_files`; no diff text inlined. **PH-250: additive `branches[]`** — `ticket_branches_payload` JOINs `git_branches → repositories` filtered by `git_branches.ticket_key == ticket.key` (the KEY STRING, e.g. `PH-250`, that `sync.py` derives from the branch NAME), surfacing the ticket's branches across ALL linked repos, each tagged with `repo_id`/`repo_slug`/`repo_name` (parallels the PH-247 commit tagging). The legacy `branch_name` single repo-agnostic string is RETAINED unchanged (frozen-shape for the FE `git.ts` consumer); `branches` is `[]` (200, not 404) when none. NO migration — the data already lives in `git_branches`; `create_branch_for_ticket` (`mcp/server.py`) stays repo-agnostic. **PH-247: repo-aware READ path** — the junction is joined by `ticket_id` ONLY (no repo filter), so a ticket's commits are ALREADY aggregated board-wide across EVERY linked repo; `ticket_commits_payload` now also JOINs `git_commits → repositories` and each `TicketCommitEntry` carries additive `repo_id`/`repo_slug`/`repo_name` (mirrors PH-246 `RepoHealth` naming; non-optional — a real commit always has a NOT-NULL `repo_id` + NOT-NULL `Repository.slug`/`name`). The endpoint's repo-presence guard (`api_ticket_commits`) was changed from `scalar_one_or_none()` (which raised `MultipleResultsFound` → 500 on any board with ≥2 repos, e.g. GXA's 3) to a `SELECT Repository.id … LIMIT 1` presence probe — 409 only when truly ZERO repos, never 500 with N≥2. NO migration (`repo_id` already on `git_commits`). Reader uses two-pass strategy: numstat first (binary detection, file list), then per-file patch with byte-cap accumulator (`git_diff_max_bytes=1 MiB` from `Settings`). Binary files yield `patch=null`+`is_binary=true`; files beyond the cap yield `patch=null`+`truncated=true` per file; top-level `truncated=true` signals any cap hit.

**G3 — Sync service** (`app/git/sync.py`): `sync_repo(session, board) → SyncResult` is the single entry-point for populating the git cache tables. Flow: (1) resolve Repository row — return `SyncResult(skipped=True)` immediately if none; (2) open repo via G2 reader; (3) upsert `git_branches` (delete stale branches); (4) walk commits via `awalk_commits(since_sha=last_synced_sha)` — delta if `last_synced_sha` is set, full backfill (up to `git_backfill_limit`) if not; (5) for each new commit: INSERT into `git_commits` ON CONFLICT DO NOTHING, then `git_commit_files` bulk insert, then per ticket-key: INSERT `git_commit_tickets` ON CONFLICT DO NOTHING — if freshly inserted, write `TicketHistory(event_type='git_commit_linked')` + publish per-ticket EventEnvelope; (6) update `repository.last_synced_sha/at`; (7) publish board-scoped `git_synced` EventEnvelope with `ticket_id='system'` sentinel. **PH-247:** the `git_commit_linked` metadata dict now also carries `repo_id`/`repo_slug`/`repo_name` (the synced `repo_row`, always present at this site) — additive JSON, no migration; legacy rows lack the keys.

**G6 — Live refresh + background poller** (`app/git/refresh.py`, `app/api/repositories.py`): `POST /api/boards/{key}/git/refresh` — **G13 hybrid auth** (PH-162): (1) `Authorization: Bearer <token>` where actor is a board admin → 202; (2) `X-Git-Refresh-Token` matching `board.roles["refresh_secret"]` via `hmac.compare_digest` → 202; bearer-without-admin → 403 (does NOT fall through to secret path — R1 safety ordering); shared-secret-not-set AND no admin bearer → 403 fail-closed; token mismatch → 401; `git_refresh_enabled=False` → **503** Service Unavailable (master kill switch, checked before all auth; body still carries `{ok:false, status:"disabled"}` so clients distinguish the kill switch from transient errors — G6 AC, PH-165). Both auth paths dispatch to the same `_locked_sync_repo` sync code path; single debounce registry. New endpoint `POST /api/boards/{key}/repository/rotate-refresh-secret` (admin Bearer only) — mints `secrets.token_hex(24)` (48 hex), stores in `board.roles["refresh_secret"]` via `flag_modified`, returns one-shot plaintext `{refresh_secret, hook_install_command}`. Old secret immediately invalidated. Subsequent `GET /boards/{key}` shows `refresh_secret: "*****"` (masked via `mask_webhook_secret`). Debounce via `RefreshRegistry.should_coalesce()` (monotonic clock, 2s default); coalesced calls return `202 {status:"coalesced"}` immediately without dispatching. Non-coalesced: `registry.mark_dispatched()` then `run_in_background(_locked_sync_repo(board_id))` returns `202 {status:"queued"}` within milliseconds. `RefreshRegistry` (module-level singleton in `refresh.py`) maintains per-repo `asyncio.Lock` and monotonic last-dispatch timestamps. `_locked_sync_repo` opens a fresh `SessionLocal()`, fetches board + repo, acquires the per-repo lock via `registry.acquire_sync_lock()`, calls `sync_repo()`. Background poller `git_poll_cron()` (lifespan task, mirrors `stale_claim_cron`) runs every `git_poll_interval_seconds` (default 30s): scans `Repository` rows with `last_synced_at < now - interval OR NULL`, skips repos whose lock is already held (`lock.locked()` pre-check — optimisation; lock is the correctness boundary), acquires lock and calls `sync_repo()` for due repos. Three new `Settings` fields: `git_poll_interval_seconds=30`, `git_refresh_debounce_seconds=2.0`, `git_refresh_enabled=True`. Poller is disabled if either flag is False/0. `mask_webhook_secret` in `boards.py` extended to also mask `refresh_secret`.

**Parser + webhook** (`app/git/parser.py`, `app/git/webhook.py`, `app/git/_linkage.py`): `parse_commit()` extracts `[A-Z]{2,5}-\d+` ticket keys and validates conventional-commit format. `webhook.py` handles GitHub push/delete/PR events. As of PH-166 the push path (`handle_push`) writes `git_commit_linked` history **through the same dedupe gate as sync** rather than unconditionally: `_linkage.ensure_commit_ticket_link(session, repo_id, commit_factory, ticket_id)` resolves (or creates) the `git_commits` row for the SHA and performs a dialect-aware `git_commit_tickets` INSERT … ON CONFLICT DO NOTHING; history is written only when the link is freshly created. So whether sync or webhook observes a (commit, ticket) pair first, history is written exactly once (no double-write on webhook-after-sync or webhook redelivery). When a board has **no** `Repository` configured the junction cannot be keyed (FK `commit_id → git_commits`), so `handle_push` falls back to the legacy unconditional write. **PH-247:** the `git_commit_linked` metadata at the webhook site also carries `repo_id`/`repo_slug`/`repo_name` — but the keys are added ONLY when `repo_row is not None` (the no-repo legacy path has `repo_row=None`, so those rows simply omit the keys, exactly like pre-PH-247 rows; readers `.get()` → None). `_linkage.py` now also owns `insert_ignore` (the shared dialect-aware gate, formerly `sync._insert_ignore`) alongside `find_ticket_by_key` / `get_system_actor_id`. When the webhook is the *first observer* it mints a minimal `git_commits` **stub** (`parents=[]`, no file rows, `committer`=push author, empty `body`); a subsequent sync no longer skips past that existing row — `_linkage.enrich_commit_row(session, repo_id, commit_values)` detects the stub (zero `git_commit_files` rows = the authoritative "sync never ran" signal) and overwrites the authoritative columns (parents/body/committer/timestamps/conventional metadata) in place (row `id` preserved → `git_commit_tickets` FK stays valid), then sync inserts the missing `git_commit_files`. An already-cached commit (has file rows) is left untouched — `enrich_commit_row` returns `None` and the loop `continue`s as before.

**G7 — Host hook installer + CLI connect_repository** (`scripts/install-git-hook.sh`, `app/cli.py:connect_repository`): Two ops-layer pieces that close the loop between a local git repo and the live refresh endpoint. `install-git-hook.sh` is a bash script (shebang `#!/usr/bin/env bash`; PH-165 switched from POSIX `sh` to use eval-free tilde expansion via `${REPO_PATH/#\~/$HOME}` — see gotcha) that installs a fire-and-forget POST hook into `.git/hooks/` (post-commit, post-merge, post-checkout, post-rewrite). Uses `git rev-parse --git-common-dir` for worktree safety — all worktrees share one hooks set under the main repo's `.git`. Idempotent: BEGIN/END marker block; re-run with same args is a no-op (`already installed (matched)`); changed secret/url replaces block in-place, preserving surrounding hook content. `connect_repository` CLI subcommand (`python -m app.cli connect_repository`) calls `upsert_repository` directly (bypasses admin auth — docker-exec host trust), manages `board.roles["refresh_secret"]` (mints a 48-hex token on first call or `--rotate-secret`; never re-prints existing secret), runs `sync_repo` backfill (up to `git_backfill_limit=2000` commits), and emits `--json` output for scripted piping into the hook installer. See `docs/operations.md` for the full self-bootstrap runbook.

**C2 — Filesystem auto-detection, per board** (`app/services/git_detect.py`, `app/api/repositories.py`): `GET /api/boards/{key}/repositories/detect` (member auth, read-only) shallow-scans **THE BOARD's own path** (PH-229; was the global `/repos/` mount root in PH-222) for git working copies and returns `DetectedReposResponse{repositories: list[DetectedRepo]}` so the frontend (PH-225/PH-230) can offer auto-detected gits when adding a repo instead of typing a path. **Scan root = the board (PH-229):** `detect_repositories(session, board)` resolves the scan START from `board.repos_path` (the board's HOST path) translated HOST→container via `repo_paths.to_container_path` (e.g. `/Users/huseyinkanat/Documents/kims` → `/repos/Documents/kims`) — so KIM scans `kims`, GXA scans `GameX`, PH scans `project-hub`, each ONLY its own subtree (PH-222 could only ever find project-hub). A null `repos_path`, a `RepoPathError` (path outside `HOST_HOME` / contains `..`), or a container root that does not exist (typo / not mounted) → `[]` (200, **never 500, never a fall-back to project-hub**). **Two roots, one allowlist (PH-229):** `_scan_sync(scan_root, …, allowlist_root=…)` splits the WALK START (`scan_root` = the board container path) from the reader's security boundary (`allowlist_root`, which STAYS `settings.repos_root` = `/repos`). Every candidate opens via the **hardened reader** `reader.open_repo(path, repos_root=allowlist_root)` — the `_validate_under_root` realpath allowlist is **unchanged** (a board path is NOT its own allowlist root), so a symlink under the board path resolving outside `/repos` is still rejected. **Root-as-candidate AND descend (PH-231, supersedes the PH-229 short-circuit):** if `scan_root` itself holds a `.git` it IS a repo (the ROOT candidate) and may ALSO contain nested INDEPENDENT repos → `_scan_git_root` adds the root (FIRST result) AND descends its subtree via the SAME `_walk_children` for nested independent repos (GXA → `GameX` + `GameXCore` + `GameXSDK` + `GameXAndroidDemoApp` = 4; live-verified). The root is the **ONLY** repo descended past its own `.git`; a nested `.git` dir is a candidate but is NOT itself descended into (no fan-out — deep vendored git behind a nested repo is structurally unreachable). Two guards bound the descent: (a) **submodule skip** — `_submodule_paths(root)` parses the root's `.gitmodules` (stdlib `configparser`), resolving each `path` to a realpath; a nested repo whose `directory.resolve()` matches is skipped (belongs to the parent). Absent/malformed `.gitmodules` → `set()` (fail-OPEN: never 500, modules surface — GameX has none, so all 3 surface). (b) **vendored prune** — `_VENDORED_DIR_NAMES` (`node_modules`, `Pods`, `build`, `.gradle`, `DerivedData`, `.cxx`, `vendor`, `Carthage`, `.build`, `target`) is a NAME filter in `_iter_child_dirs` that prunes a denylisted child from BOTH the candidate set AND the descent frontier (keeps a shallow `node_modules/.git` out; the deep `GameXCore/src/main/cpp/.../LiteRT` TFLite git is additionally unreachable because GameXCore, a repo, is never descended into). A realpath `seen` set dedups (a symlinked child resolving back to the root is not double-listed); the root counts toward `max_results`. Otherwise (no `.git` at the root) the immediate children are shallow-scanned to depth ≤ 2 (`_scan_sync` via `asyncio.to_thread` — never blocks the loop): an immediate child holding a `.git` (dir OR file/worktree) is a candidate; a child WITHOUT `.git` is descended ONE more level (a parent dir holding several repos); a dir that already IS a repo is **never** descended into (no `node_modules/.git` fan-out). `_MAX_DEPTH` stays 2 (the modules are at depth 1; deep vendored git is out of reach). Per candidate: `remote_url` = the `origin` remote URL (fallback first remote, else `None`), `default_branch` = `reader._detect_default_branch(repo)`, `provider_guess` = pure-substring host check on `remote_url` (`github.com`→`github`, `gitlab`→`gitlab`, else/None→`local`; reuses the `Provider` literal so it drops straight into a `POST /repositories` `RepositoryCreate.provider`), `already_linked` = candidate realpath ∈ the resolved `local_path` set from `list_repositories(session, board)` (board-scoped — for PH this matches the relocated `local_path=/repos/Documents/project-hub`, so PH's own repo shows `already_linked=true`). Bounded + safe: `max_results=100` cap + `time_budget_seconds=5.0` wall-clock budget (both overridable in tests); a missing/empty/permission-denied root, a non-git dir, or any `GitReaderError`/`git.GitError` → skip that entry and return 200 with a partial/empty list — **never a 500**. The `DetectedRepo` shape (`local_path`/`name`/`is_git`/`remote_url`/`default_branch`/`provider_guess`/`already_linked`) is the **frozen contract** (unchanged by PH-229 — only the scan root moved) published for PH-225, mapping 1:1 onto `RepositoryCreate` for one-click add. The `repos_root=` kwarg on `detect_repositories`/`_scan_sync` is retained as a **TEST override** (self-contained temp tree, scan_root == allowlist_root); production omits it so the board drives the root. Read-only: creates no `Repository` rows and never writes to the filesystem. **Live multi-board verified (PH-229; extended PH-231):** KIM→`kims` (not linked), PH→`project-hub` (already_linked=true) each resolve exactly their own single repo (no fan-out into subdirs); GXA→**4** candidates `GameX` (root, first) + `GameXCore` + `GameXSDK` + `GameXAndroidDemoApp` (the 3 independent nested repos), with the deep LiteRT/TFLite vendored git correctly EXCLUDED; null/RepoPathError/typo paths return `[]`.

**C1 — Per-board path + HOST↔container translation** (`app/services/repo_paths.py`, `app/db/models/core.py`, `docker-compose.yml`): each `Board` now carries `repos_path` (String(500), nullable) storing the board's **HOST** filesystem root (e.g. `/Users/huseyinkanat/Documents/kims`) — the user-meaningful path matching Finder/CLI, NOT the container path. The single broadened backend bind-mount `${PROJECTS_ROOT:-${HOME}}:/repos:ro` (was a single `.../project-hub:/repos/project-hub` sub-path) maps the host `$HOME` onto the container `/repos` (`settings.repos_root`), so translating a stored host path to the path the **hardened reader** can `open_repo` is a pure string substitution. `repo_paths.py` is the **single shared implementation**: `to_container_path(host)` swaps the `settings.host_home` prefix (`HOST_HOME`, default `/Users/huseyinkanat`, env-overridable) for `repos_root` (`/Users/huseyinkanat/Documents/project-hub` → `/repos/Documents/project-hub`; `/Users/huseyinkanat/AndroidStudioProjects/GameX` → `/repos/AndroidStudioProjects/GameX`); `to_host_path(container)` is the inverse. Both validate **absolute-only + reject `..` traversal + reject paths outside the root**, raising `RepoPathError` (a `ValueError` subclass) instead of returning a silently-wrong path — PH-229 consumers catch it and skip the board gracefully (mirrors detect's skip-and-continue). Dependency-light (config only), pure, unit-testable. `BoardResponse.repos_path` exposes the value (read surface only — PATCH editability is deferred to PH-230; `BoardUpdate` is intentionally unchanged). Migration `20260608_0010` backfills the 6 known boards with their verified host paths (keyed by board `key`, `WHERE repos_path IS NULL` → idempotent) and **relocates the PH repo's `local_path` from `/repos/project-hub` → `/repos/Documents/project-hub`** in lock-step with the broadened mount (the new path still satisfies the `/repos/` allowlist — no validator change; the cache is repo_id-keyed so the 392-commit / 2-branch PH cache survived the relocation, verified live). PH-228 publishes the field, mount, and helper only; the detect/sonar **consumers** that call `to_container_path` land in PH-229.

**Cache tables** (migration `20260604_0007`): `git_commits` (sha unique per repo), `git_branches` (name unique per repo, refreshed each sync), `git_commit_files` (immutable per commit), `git_commit_tickets` (junction, unique (commit_id, ticket_id) = dedupe gate).

## Design decisions (recent)

- Default-branch head FORCED to `commits[0]` via a primary ready-set key + topo helper split for cognitive complexity [PH-266 review] — the first PH-266 cut relied on the tie-break `(committed_at, sha)` to keep the default head at index 0, which only holds when the default head happens to be the newest commit. On real data an OPEN side-branch tip with a newer `committed_at` could become `commits[0]`. The revision passes `default_head` into `_topological_order` and makes `sha == default_head` the PRIMARY ordering key (`(is_default_head, committed_at, sha)`), so the default head wins index 0 the moment it is ready — regardless of timestamp. NOTE the invariant only applies when the default head is a SOURCE (nothing in-window stacked above it): if a feature branch is genuinely built ON TOP of the default head, that child correctly precedes it (forcing the head to index 0 would invert a real first-parent edge). The same revision SPLIT the Kahn loop into two pure helpers — `_count_pending_children` (in-window child counts) and `_release_ready_parents` (decrement + sorted-insert on emit) — to drop `_topological_order`'s nesting below the Sonar S3776 cognitive-complexity threshold (the dead `children` dict that the first cut left in was also removed, and `pending_children` now uses `dict.fromkeys(in_window, 0)` for Sonar S7519). Real-data re-probe (host Node, REAL FE layout over the live 200-commit PH payload): first-parent topo violations **1→0**; the targeted false ring on the fully-merged tip `945e4cd4` is GONE. Two open rings REMAIN and are both LEGITIMATE — `304ed596` (a genuinely unmerged feature tip, ahead=1) and `7700a2f9` (a window-edge dangling leaf whose merge child falls outside the 200-commit window) — neither is the topo-inversion bug, and both are present under the legacy ordering too.

- Git graph served in topological order, fixing a false "unmerged" ring [PH-266] — `graph_payload` previously returned `commits[]` ordered `committed_at DESC, sha DESC`, which is NOT topological: on real board PH history exactly 1/150 commits (`405523f9`) had its first parent (`945e4cd4`, a fully-merged tip) sort ABOVE it on a `committed_at` tie. The FE lane layout (`assignLanes`/`computeLanePaths`) then isolated `945e4cd4` into its own single-row span so it could never inherit the "merged" classification → it rendered a dashed open/unmerged ring (the primary remaining visible bug after PH-265's lane-leak fix). **Fix is backend-only** (the load-bearing one): a NEW pure helper `_topological_order(commits)` does a Kahn sort newest-first (child before parent) over IN-WINDOW parent edges, tie-breaking the ready set by `(committed_at, sha)` so it (a) is deterministic and (b) keeps the default-branch head — depended on by nothing — at index 0 (the FE seeds lane 0 from `commits[0]`). `graph_payload` now fetches the FULL candidate set (no DB `.limit`), topo-sorts, THEN truncates to `limit` (truncate-then-sort would let the window drift and re-introduce the inversion). Real-data probe (host Node, REAL `assignLanes`+`computeLanePaths` over the 150-commit PH payload): first-parent parent-above-child violations 1→0, `computeLanePaths` openTips 1→0. A cycle guard appends any never-emitted commit in deterministic order so the output is never shorter than the input. - G6 poller skips locked repos via `lock.locked()` pre-check [PH-155] — avoids queuing behind an in-flight refresh (the refresh already covers the sync); note: pre-check is racy but harmless (both paths call idempotent `sync_repo`; lock is the correctness boundary, not the pre-check)
- G5 live reader on hot path with byte cap [PH-154] — patches computed on demand via `git diff` subprocess (two-pass: numstat then per-file patch); `git_diff_max_bytes=1 MiB` prevents DoS from huge commits; no patch caching in G5 (in-memory LRU deferred to G6+ if p95 latency warrants)
- G5 two-pass numstat-then-patch strategy [PH-154] — numstat is O(files) without loading patch bodies, detects binaries cheaply, allows early-exit before expensive per-file subprocess fan-out; single-pass `git diff -p` would require parsing a giant blob in Python
- G5 ticket commits endpoint is cache-only, no inline diff [PH-154] — UI calls `GET /git/commits/{sha}/diff` on demand per sha; inlining diffs in the list response would multiply payload size; service layer joins `git_commit_tickets → git_commits LEFT JOIN git_commit_files` aggregate via SQL (no N+1)
- G5 three-dot range semantics (`base...head`) [PH-154] — matches GitHub/GitLab PR-diff conventions; merge-base anchored so `main...feature` shows only feature-branch-specific changes; two-dot `base..head` available via existing commits endpoint
- `--no-ext-diff` on every patch-generating diff call [PH-154] — blocks `diff.external` RCE from local `.git/config` (reviewer-confirmed: injecting `diff.external=/path/script` in `.git/config` executed the script without this flag); `diff.external` is absent from `_SAFE_CONFIG_FLAGS` because `-c diff.external=` (empty string) causes git to exec `""` resulting in "cannot run : No such file or directory"; `--no-ext-diff` is the correct per-call mechanism — it disables external diff drivers without any side-effect on patch output; regression test `test_diff_text_ext_diff_not_triggered` uses a script-file probe (not inline sh -c) to verify this invariant
- G4 read API extends `repositories.py` router (single git router, no parallel `app/api/git_read.py`) [PH-153] — G1 docstring already promised G2-G6 would add routes here; keeps all `/git/*` reads in one file, minimises `main.py` churn
- ahead/behind computed via bounded BFS over cached `git_commits.parents` JSON column; returns `null` on overflow (BFS exceeds `git_backfill_limit=2000`) [PH-153] — exact calculation would need recursive CTE or in-memory graph; pragmatic compromise documented in `GitBranchEntry.ahead/behind` schema field comments
- repo-not-configured → 409 `RepoNotConfigured` (new `ProjectHubError` subclass) [PH-153] — empty arrays would be ambiguous (sync not run yet vs. no repo attached); 409 makes the prerequisite explicit for G8 frontend
- `app/git/_linkage.py` extracted from `webhook.py` to be shared by `sync.py` — avoids duplication of `find_ticket_by_key` + `get_system_actor_id`; underscore prefix = internal to `app/git/` [PH-152] — smallest safe refactor, backward-compat aliases in webhook.py kept for existing test imports
- sync.py uses `git_commit_tickets` unique constraint as dedupe gate — if webhook lands first, sync's INSERT returns no rows and history write is skipped; first-observation wins (timestamps anchored to first link) [PH-152]. The reverse asymmetry (webhook lands after sync) was fixed in [PH-166] by routing the webhook through the same gate — both directions now write history exactly once.
- board-scope `git_synced` envelope reuses `EventEnvelope` with `ticket_id="system"` sentinel — same pattern as `system_degradation` in `bus.py`; the `ticket:system` channel has no subscribers (harmless extra PUBLISH) [PH-152]
- `_insert_ignore` branches on dialect: PostgreSQL uses `INSERT … ON CONFLICT DO NOTHING RETURNING id` (reliable RETURNING to detect new vs. conflict); SQLite uses a pre-check SELECT then INSERT (no RETURNING support in older SA) [PH-152] — keeps tests runnable on in-memory SQLite without mocking
- `git_backfill_limit=2000` in `Settings` — protects against OOM on large repos; G6 manual refresh may surface the cap to callers; oldest commits below the cap are absent from cache [PH-152]
- GitPython chosen over dulwich for reader (rename detection, unified diff fidelity) [PH-151]
- Repository model uses string `provider` + CHECK constraint instead of DB Enum (migration flexibility) [PH-150]

## Known gotchas

- `graph_payload` MUST topo-sort the FULL set then truncate — not truncate-then-sort [PH-266] — the DB query intentionally has NO `.limit`; the cap is applied in Python AFTER `_topological_order`. If you re-add a DB `LIMIT` (e.g. for "performance"), a parent just outside the window can be dropped while its child stays, or the committed_at slice can re-invert a first-parent edge, re-introducing the false "open/unmerged" ring (PH-266's exact bug). The cached window is already bounded by what sync persists, so the full fetch is fine. Also: `_topological_order` takes `default_head` and ranks it as the PRIMARY ready-set key (`sha == default_head` before `(committed_at, sha)`) so the default-branch head is `commits[0]` (the FE `assignLanes` seeds lane 0 from `commits[0]`) EVEN when an open side-branch tip is newer — do NOT drop the `default_head` arg back to a pure timestamp tie-break, that regresses lane anchoring whenever an open branch out-dates main. CAVEAT (not a bug): the head-first guarantee only holds when the default head is a SOURCE (no in-window children). If a feature branch is committed ON TOP of the default head, that child correctly precedes it in the topo order (so on a dev DB where the current work-branch is stacked on main, `commits[0]` is the work-branch tip, not main — this is correct topo order, identical to the legacy ordering, NOT a regression). Only `graph.commits[]` is topo-ordered — do NOT apply `_topological_order` to the `commits`/`commits/{sha}` pagination paths (their `before=<sha>` cursor relies on plain `committed_at DESC, sha DESC`).
- On the ticket git-activity surface, BRANCHES join by `ticket_key` (string) but COMMITS join by `ticket_id` (UUID) — do NOT unify them [PH-250] — `ticket_branches_payload` filters `git_branches.ticket_key == ticket.key` (the KEY STRING like `PH-250`, which `sync.py` extracts from the branch NAME via `TICKET_KEY_RE`), while `ticket_commits_payload` joins `git_commit_tickets.ticket_id == ticket.id` (the UUID). There is NO `ticket_id` column on `git_branches` and no `ticket_key` join on the commit junction — each key is the only correct one for its own source table. A dev "harmonizing" the two would break one of them. Consequence: a branch whose NAME does not embed the ticket key (free-form name → `ticket_key=NULL`) does NOT appear in `branches[]` — this matches `git_branches`' name-derived nature and is acceptable (the branch name IS the linkage source). `branches[]` reflects LIVE repo state (sync purges vanished branches), not history.
- The ticket commits endpoint joins by `ticket_id` ONLY = board-wide across repos by design [PH-247] — `ticket_commits_payload` does NOT filter by `repo_id`, so a ticket linked to commits in multiple repos returns ALL of them in one fetch, each tagged with its own repo. This is intentional (the per-ticket "all your git activity" surface). The per-repo graph/branch/commits views are the OPPOSITE — they use the `?repo=` selector and are scoped to one repo. Don't "fix" the ticket endpoint to filter by primary repo; that would re-drop non-primary commits (the exact bug PH-247 closed).
- FE drill-down into a non-primary repo's commit MUST pass `?repo=<slug>` or `commit_detail` 404s [PH-247] — `GET /api/boards/{key}/git/commits/{sha}` (and its `/diff`) defaults to the board's PRIMARY repo when no `?repo=` selector is given. A `TicketCommitEntry` from a NON-primary repo carries `repo_slug` precisely so the FE (PH-249) threads it into `api.git.getCommit(boardKey, sha, {repo})` / the DiffViewer fetch. No backend change is needed for this (the selector already exists) — but if the FE forgets to pass `repo_slug`, a non-primary commit's diff 404s even though the commit shows in the ticket list.
- `git_commit_linked` metadata repo keys are conditional at the webhook site [PH-247] — `sync.py` always has a `repo_row` (it early-returns if none), so its metadata always carries `repo_id`/`repo_slug`/`repo_name`. But `webhook.py`'s `_link_push_commit` runs on the legacy no-repository path too (`repo_row=None`), where the keys are deliberately OMITTED rather than written as `None` — keeping no-repo rows shape-identical to pre-PH-247 legacy rows. Any consumer of `git_commit_linked` metadata MUST `.get("repo_slug")` with a None default; never index `meta["repo_slug"]` (KeyErrors on legacy + no-repo rows).
- Detect route must be declared BEFORE `/repositories/{selector}` [PH-222] — `GET /repositories/detect` is a static path that would be shadowed if a `GET /repositories/{selector}` route existed (FastAPI matches in declaration order; the literal `detect` could be captured as a selector value). Today there is no GET-on-`{selector}` route (only `DELETE /repositories/{selector}` and `POST /repositories/{selector}/set-primary`), so there is no live collision — but it is declared right after `POST /repositories` and before the `{selector}` routes to keep the ordering safe if a `GET /repositories/{selector}` is ever added. If you add one, put it AFTER `detect`.
- Detect descends a no-`.git` child but stops at a real repo — EXCEPT the ROOT [PH-222, amended PH-231] — the depth-2 walk in `_walk_children` only goes one level deeper into a child that has **no** `.git` (a container dir holding several repos). A child that IS a repo is appended and NOT descended into, so a vendored/submodule clone inside a detected CHILD repo (`outer/vendor/nested/.git`) is never returned as a separate candidate (no `node_modules/.git` fan-out). **PH-231 exception:** when the SCAN ROOT itself is a repo, `_scan_git_root` DOES descend past the root's own `.git` (and only the root's) to surface nested INDEPENDENT repos — but it still never descends INTO those nested repos, so the no-fan-out invariant holds one level down. The wall-clock budget (`time_budget_seconds`, default 5.0s) and `max_results` (default 100) cap the walk regardless; a `time_budget_seconds=0.0` returns `[]` immediately (the deadline is already past) — fine for "never hang" but it means a zero budget yields nothing, so keep the production default positive.
- Independent nested repo vs submodule vs vendored — the three-way distinction [PH-231] — under a git-root board path (`_scan_git_root`), a nested `.git` dir at depth 1 is one of three things: (1) an **independent** repo (own `.git`, NOT in the root's `.gitmodules`, name not denylisted) → SURFACED; (2) a **submodule** (its `path` is registered in the root's `.gitmodules`) → SKIPPED (belongs to the parent); (3) **vendored** (under a `_VENDORED_DIR_NAMES` dir like `node_modules`/`build`/`.cxx`) → PRUNED before it is even a candidate. Two non-obvious traps: (a) `_submodule_paths` fail-OPEN — an absent OR malformed `.gitmodules` returns `set()`, so a real submodule could surface as a candidate (the SAFE default — worst case an extra candidate, never a 500; GameX has NO `.gitmodules` so all 3 modules surface, which is the wanted behaviour). Matching is by **realpath equality** (`(root / path).resolve()` vs `directory.resolve()`), so a relative-vs-absolute `path` mismatch cannot cause a false skip. (b) Only the ROOT's `.gitmodules` is parsed — submodules nested deeper than depth 1 are NOT resolved (and need not be: we never descend INTO a nested repo, so a deeper submodule is unreachable anyway). If you ever raise `_MAX_DEPTH` or start descending nested repos, this assumption breaks — re-parse `.gitmodules` per descended repo.
- `scan_root` ≠ `allowlist_root` — never collapse them [PH-229] — `_scan_sync` takes TWO roots: `scan_root` (the WALK START = the board's container path, e.g. `/repos/Documents/kims`) and `allowlist_root` (the hardened reader's `repos_root=` boundary, which MUST stay `settings.repos_root` = `/repos`). If you "simplify" by passing the board path as the reader's `repos_root`, you re-introduce the exact vulnerability PH-229 guards against: `_validate_under_root` would then allow anything under the board path (a board path becomes its own allowlist root), so a symlink escaping `/repos` but staying under the board dir would pass. The two are split precisely so a sub-tree scan keeps the mount-root security boundary. The `allowlist_root` kwarg defaults to `scan_root` ONLY for the bounds unit tests that pass a self-contained temp tree; production always passes the real `/repos`.
- Detect now scans `board.repos_path`, not `settings.repos_root` — TEST override changed [PH-229, supersedes PH-222] — `detect_repositories` no longer scans the global mount root; it resolves the scan START from `board.repos_path` via `to_container_path`. The `repos_root=` kwarg is now a **TEST-only override** (when given it is the scan start AND the allowlist, a temp tree), NOT the production root. **An API/route test that needs the route to see a temp tree can no longer just set `get_settings().repos_root`** — it must (1) point `settings.host_home` + `settings.repos_root` at the temp dir so `to_container_path` maps into it, and (2) set `board.repos_path` to a HOST path under that synthetic `host_home`. See `tests/test_git_detect.py::_point_translation_at`. A board with `repos_path=None` (the default in the `seed` fixture) now returns `[]` from the route regardless of `settings.repos_root` — the old "set repos_root, hit route, see repos" pattern (PH-222 `test_route_member_detect_200`) was updated to the new per-board contract.
- Partial unique index needs BOTH `postgresql_where` AND `sqlite_where` [PH-221] — `uq_repository_one_primary` (≤1 primary per board) is a partial unique index. SQLAlchemy ignores `postgresql_where` on SQLite, so with only the Postgres predicate the index **degrades to a full `UNIQUE(board_id)` on the in-memory test DB** — which silently forbids a board from having more than one repo (the exact 1:N capability the ticket adds), making multi-repo tests fail with `UNIQUE constraint failed: repositories.board_id`. Fix: pass `sqlite_where=text("is_primary = 1")` alongside `postgresql_where=text("is_primary = true")` (both must be `sa.text(...)`, not plain strings — a bare str raises `'str' object has no attribute '_compiler_dispatch'`). The sibling `uq_board_active_workflow` on `BoardWorkflow` has the SAME latent issue (Postgres-only predicate) but its tests never insert two inactive workflows for one board, so it was never exposed. The service-layer one-primary invariant (`set_primary`/`add_repository`) is the cross-dialect backstop regardless.
- `repo` selector slug-vs-id precedence [PH-221] — the `/git/*` `repo` query param accepts EITHER a slug or a row UUID. `resolve_repository` tries `uuid.UUID(selector)` first; a successful parse + match wins over a slug match (id precedence). Slugs are `[a-z0-9_-]` derived from short basenames, so a 36-char hyphenated-hex collision is only theoretical. Frontend should prefer the slug (human-stable, URL-safe). Omitted `repo` → primary; an explicit selector matching nothing → 404 (distinct from the 409 a board with zero repos returns).
- `install-git-hook.sh` now requires bash, not POSIX sh [PH-165] — the eval-free tilde expansion `${REPO_PATH/#\~/$HOME}` is a bash parameter-substitution form that dash/ash do not support; shebang was changed to `#!/usr/bin/env bash`. Validate with `bash -n scripts/install-git-hook.sh`, not `sh -n`. The script is invoked directly (`./scripts/install-git-hook.sh ...`) or via `bash scripts/install-git-hook.sh ...`; the `hook_install_command` emitted by `connect_repository --json` already uses `bash scripts/...`.
- G13 rotate invalidates all existing hook installs [PH-162] — after `POST /repository/rotate-refresh-secret`, any hook sending the old secret receives 401. Re-install the hook via `scripts/install-git-hook.sh` with the new secret immediately. Admin Bearer path is unaffected (uses actor token, not the refresh secret).
- G13 Bearer alt-auth loops ALL active actors via `verify_token` (bcrypt) [PH-162] — for every request with `Authorization: Bearer` header, the endpoint loads all active actors and bcrypt-checks each. Same cost as the standard `current_actor` dependency. Only triggered when the header is present; anonymous hook calls (no `Authorization`) skip this path entirely with zero overhead.

- G7 secret in `.git/hooks/` plaintext [PH-156] — `.git/` is git-ignored by definition, never committed. On shared/multi-user machines: `chmod 700 .git/hooks/` restricts read. After `--rotate-secret`, the old hook files have a stale token (GET /git/refresh → 401); they log to stderr but never block commits. Re-install hook immediately after rotation.
- G7 `curl` not found silences hook [PH-156] — hook body checks `command -v curl` before executing; if curl is absent the hook silently no-ops. Install warns at install time. Poller (G6) is the fallback — commits appear in graph within 30s even without curl.
- G7 bare repo not supported [PH-156] — `git rev-parse --git-common-dir` returns `.` for bare clones; installer exits 1 with "bare repositories are not supported". Standard working-tree clone required (G2 reader also requires non-bare).

- G6 registry is volatile (resets on restart) [PH-155] — `_last_request_monotonic` is in-process memory; on restart all debounce state is lost. First refresh request post-restart triggers a sync regardless of recent activity. This is deliberate (no stale coalesce decision survives a process boundary; durable record is `repository.last_synced_at`).
- G6 single-process scope [PH-155] — `asyncio.Lock` does not span uvicorn workers (`--workers >1`). Current deployment is single worker; if scaled, replace `RefreshRegistry` with Redis SETNX (settings.redis_url is already wired). The `RefreshRegistry` public API (get_lock / should_coalesce / acquire_sync_lock) is the abstraction boundary for that swap.
- G6 debounce coalesces multiple pushes into one `git_synced` WS envelope [PH-155] — a 2s burst of 10 commits gets one envelope listing all commits (not 10 envelopes). Frontend must handle multi-commit payload; G8 already expects `new_commit_shas: list[str]`.
- Cache-vs-FS truth divergence after force-push [PH-154] — diff endpoint hits live FS; if a commit was force-pushed away after sync, `GitPython.commit(sha)` raises `BadName` (404) even if `git_commits` row still exists. This is correct behaviour (truth = FS), but can surprise callers who see a cached commit summary but 404 on its diff. Mitigation: G6 refresh will detect force-push and remove stale cache rows.
- Per-file subprocess fan-out for large refactor commits [PH-154] — `diff_text` issues one `git diff` subprocess per file (after the numstat pass). For a 500-file refactor this is 501 forks. Mitigation: numstat pass gives early visibility into N; future optimisation could fall back to single `git diff -p` + Python-side split for very large N. Deferred — measure p99 in production first.
- UTF-8 replace policy for mixed-encoding files [PH-154] — patch bytes decoded with `errors='replace'`, so a binary-looking but non-detected-binary file (e.g. Latin-1 encoding without NUL bytes) will show `�` replacement characters in the patch field. Frontend should handle gracefully.
- Cursor pagination in `GET /git/commits` uses `committed_at` not a sequence id — duplicate timestamps (rapid-fire commits in the same second) are stabilised by a `sha DESC` tie-break in `ORDER BY committed_at DESC, sha DESC`. Two commits with identical timestamp + sha prefix collision can still cause a commit to appear on both pages; acceptable edge case. [PH-153]
- `GET /git/commits/{sha}` accepts both 40-hex and short sha (≥7 chars matching `git_commits.sha LIKE sha%`); if ≥2 rows match the prefix the endpoint returns 404 (not 500). Artificially seeded test commits whose prefixes collide will trigger this path — keep test sha values distinct in their first 8 chars. [PH-153]
- Force-pushed default branch: `walk_commits(since_sha=X)` raises `GitCommandError` when X is unreachable; `sync.py` catches this and falls back to full backfill (idempotent via unique constraints). If even the full backfill fails, `SyncResult(skipped=False, new_commits=0)` is returned without raising. [PH-152]
- Webhook-after-sync double-write asymmetry: FIXED [PH-166]. Previously `sync.py` checked `git_commit_tickets` before writing history but `webhook.py` did NOT, so a webhook arriving after sync wrote a second `git_commit_linked` row for the same (commit, ticket). `handle_push` now goes through `_linkage.ensure_commit_ticket_link` (the same gate sync uses); history is written only on a fresh junction insert, so webhook-after-sync, sync-after-webhook, and webhook redelivery all yield exactly one row. Caveat: boards with no `Repository` row still use the legacy unconditional write (no `git_commits` row to key the junction). [PH-152, PH-166]
- Webhook-first stub must be enriched by sync, not skipped [PH-166]. `ON CONFLICT DO NOTHING` (and `insert_ignore`) only protect the *insert* — they do **not** update existing columns. So a webhook-minted stub (`parents=[]`, 0 file rows, `committer`=push author) is NOT enriched by a later `INSERT … ON CONFLICT`; sync must explicitly UPDATE it. `enrich_commit_row` does this, gated on the **absence of `git_commit_files` rows** (not on `parents==[]` — a legitimate root commit has empty parents too, so that test would re-enrich real root commits every sync). If you add a code path that creates a partial `git_commits` row, ensure sync's enrichment branch (the `insert_ignore == False` arm) still runs for it, or commit-detail views show 0 files / 0 additions and the branch-graph ahead/behind BFS reads `parents=[]` and breaks. [PH-166]
- `session.flush()` required before `publish_ticket_event` — `history.id` must be non-null (generated by flush, not commit). `sync.py` flushes per-commit; ensure the order is `add(history) → flush → publish`. [PH-152]
- `git_commit_files` has no unique constraint on `(commit_id, path)` because rename pairs can produce duplicate paths (old + new both map to the same `b_path`). Use `commit_id` index only; no deduplication at insert. [PH-152]
