# Backend

> FastAPI 0.115 + SQLAlchemy 2 async + Alembic + PostgreSQL 16 + Redis 7 service that powers ProjectHub's ticket state machine, MCP tool catalog, and WebSocket fan-out.

## Current behavior

The backend is a single ASGI app (`backend/app/main.py`) that exposes ProjectHub as **two parallel surfaces over the same domain logic**: a REST API under `/api/*` for the React frontend and an MCP catalog under `/mcp/*` for agent clients (Claude Code, Jarwis sub-agents). Both surfaces route through identical service functions in `backend/app/services/`, so permission checks, history writes, and event publication are uniform regardless of caller. The app boots with a `lifespan` context manager that starts the Redis-backed `EventBus` and a `stale_claim_cron` background task, then mounts CORS plus the routers `auth`, `actors`, `boards`, `tickets`, `notifications`, `preferences`, `git`, `repositories` (PH-150 G1), `mcp_server`, and `websocket`. Centralized exception handlers (`app/core/exceptions.py`, registered via `register_exception_handlers`) translate domain errors — `NotFound`, `PermissionDenied`, `InvalidTransition`, `FieldGateNotMet`, `AlreadyClaimed` — into structured HTTP responses with consistent payload shapes.

Persistence is async SQLAlchemy 2 against PostgreSQL (with SQLite/`aiosqlite` fallback for tests). The ORM (`app/db/models/core.py`) models `Actor`, `Board`, `BoardMembership`, `Workflow`, `BoardWorkflow` (junction for per-board workflow ownership — PH-97), `Ticket`, `Comment`, `Notification`, `TicketHistory`, `UserPreference`, and `Repository` (PH-150 G1 — git config, 1 board : 0..1 repo, FK `boards.id` ondelete=CASCADE). **PH-272** adds the concept-tag data layer: `ConceptTag` (GLOBAL taxonomy, NO `board_id` — mirrors `Actor`/`Workflow`; globally-unique `slug` via `uq_concept_tag_slug`), `TicketConceptTag` (M2M junction tickets↔concept_tags, `uq_ticket_concept_tag (ticket_id, concept_tag_id)`, both FKs CASCADE), and `ConceptTagLink` (DIRECTED self-referential tag↔tag edge `source_tag_id`→`target_tag_id` + nullable `relation` label, explicit `foreign_keys=[...]` on each relationship to resolve the self-FK ambiguity). JSON columns are dialect-aware (`JSONB` on Postgres, plain `JSON` elsewhere) and arrays degrade similarly. Tickets carry workflow-driven `state` plus rich domain fields (`technical_depth`, `impact_analysis`, `test_plan`, `acceptance_criteria`, `steps_to_reproduce`, `branch_name`, `labels[]`, `claimed_by`/`claimed_at`, `agent_phase`). Schema evolution is managed by Alembic — versions live in `backend/app/db/migrations/versions/` (currently 11 revisions, most carrying a `PH-XX` slug). **PH-228** adds `Board.repos_path` (String(500), nullable) — the board's HOST filesystem root (e.g. `/Users/huseyinkanat/Documents/kims`), backfilled for the 6 known boards by migration `20260608_0010` and translated to the in-container `/repos` path by `services/repo_paths.to_container_path` (the `host_home`/`HOST_HOME` setting + the broadened `${HOME}:/repos:ro` mount; full design on [[components/git-integration]]). Authentication is bearer-token based: `Actor.token_hash` stores a bcrypt hash (`app/core/security.py:hash_token` / `verify_token`); `api/deps.py:current_actor` resolves the request token by iterating active actors and `verify_token`-matching the bearer credential. Permission checks are board-scoped (`app/core/permissions.py:require_permission`) and understand wildcards (`*`, `state.transition:*`, `ticket.release:*`, `ticket.update_field:<field-list>`), plus an `:if_assignee` suffix that treats `claimed_by` as equivalent to `assignee_id` so a sub-agent that claimed without `assign_ticket` still passes the gate.

The MCP catalog (`app/mcp/server.py`) exposes the same tools over two transports — a legacy REST shape (`GET /mcp/tools`, `POST /mcp/call/{tool}`) and full MCP JSON-RPC 2.0 (`POST /mcp` with `initialize` / `tools/list` / `tools/call`) — both delegating to one `_dispatch_tool` so behavior, permissions, and history are identical. Headline tools: `list_boards`, `get_board`, `query_tickets`, `get_ticket`, `get_state` (~200-char Coordinator self-verify probe), `get_ticket_slice` (caller-projected field subset), `create_ticket`, `update_ticket`, `assign_ticket`, `transition_state`, `add_comment`, `claim_ticket`, `release_ticket`, `update_agent_phase`, `create_branch_for_ticket`, plus workflow CRUD. Write tools default to a minimal response (`{ok, id, updated_fields, state}`) and opt into the full ticket payload via `verbose=true` — a deliberate budget choice that lets Coordinator self-verify cheaply. The ticket state machine lives in `services/tickets.py:transition_ticket_state` and consults the active workflow's `transitions` list + `allowed_roles` for role gating, with `assignee` treated as equivalent to `claimed_by` so an agent that claimed without `assign_ticket` still passes the gate. Field gates (`_missing_gate_fields`) are workflow-configurable (`services/workflows.py:get_field_gates_for_ticket_transition`) — e.g. `in_review → in_test` may require `test_plan`. Every state mutation writes a `TicketHistory` row and publishes an `EventEnvelope` via the Redis pub/sub `EventBus` (`app/events/bus.py`); the `websocket` router subscribes per-board / per-ticket channels and streams envelopes to connected clients, with exponential-backoff reconnect and a `system_degradation` fallback envelope when Redis is unreachable. A separate `stale_claim_cron` (`services/stale_claims.py`, 60s interval, 5-minute timeout) sweeps tickets whose `claimed_at` exceeds the heartbeat threshold and auto-releases them — the safety net that lets sub-agents crash without leaving a dangling lock. A third lifespan task, `sonarqube_poll_cron` (`services/sonarqube.py`, PH-193), polls a self-hosted SonarQube Community Build for each board's main-branch quality metrics, upserts the latest snapshot into the `sonarqube_metrics` table (1 board : 0..1 row, unique `board_id`), and publishes a `sonarqube_synced` envelope on `board:{id}`; it is gated on `settings.sonarqube_enabled` (default False → task never created, no-op) and surfaces as `BoardResponse.health` (eager-loaded via `selectinload(Board.sonarqube_metric)`, mirroring `repository`). The `app/cli.py` module provides operational commands (board bootstrap, `create_jarwis_actors`, `update_board_roles`) used by `jarwis-init.sh` and manual maintenance. Git commit parsing (`app/git/parser.py`) extracts `[A-Z]{2,5}-\d+` ticket keys from messages and validates conventional-commit format for the webhook ingestion in `app/git/webhook.py`.

## Design decisions (recent)

- Cross-board bipartite concept-graph endpoint `GET /api/graph` [PH-274] — child 3/7 of epic PH-271; the read-only topology endpoint that feeds the Obsidian-style `/space` view (PH-277). New GLOBAL router `app/api/graph.py` (`/api/graph`, registered after `concept_tags.router`) + pure-assembly service `app/services/graph.py`; new `GraphNode`/`GraphEdge`/`GraphResponse` schemas. **Bipartite** nodes = tickets + concept tags, disambiguated by a TYPE-PREFIXED `id` (`ticket:<uuid>` / `tag:<uuid>`) — the SOLE disambiguator (a ticket UUID and a tag UUID could otherwise collide in the id namespace); every node ALSO carries a redundant `type` discriminator so the frontend styles/filters without parsing the id. Three edge types: `has_tag` (ticket↔tag from the `TicketConceptTag` junction — a tag on tickets in 2 boards yields 2 edges sharing one tag node = the cross-board join), `tag_link` (tag↔tag from `ConceptTagLink`, directed source→target, `relation` carried, reverse pair NOT deduped — render-layer concern), `epic` (ticket↔ticket parent→child from `Ticket.epic_id`, emitted only when the parent node is in the set). **N+1-free (AC6)**: THREE bounded one-shot queries — Q1 tickets `selectinload(concept_tag_links→concept_tag, board)` (graph-local minimal options, NOT `_ticket_load_options` which over-fetches reporter/assignee/workflow), Q2 all `ConceptTagLink` with both endpoints eager, Q3 full `ConceptTag` map (node identity + orphan policy). `selectinload` issues a FIXED number of follow-up SELECTs regardless of row count → statement count is CONSTANT across 1 vs 50 tickets (test asserts this via a `before_cursor_execute` counter). Filters `?board=<key>` (case-insensitive, 404 unknown) + `?tag=<slug>` (1-hop subgraph) compose as INTERSECTION; a uniform final invariant — emit an edge IFF both endpoints survived into the node set — makes every filter mode correct by construction (no per-filter edge bookkeeping). Orphan tags (no junction + no link): INCLUDED as standalone nodes in the unfiltered graph, EXCLUDED under filters. Permission reuses the PH-273 global `tag.read` gate (`concept_tags._require_tag_read`) — the graph exposes cross-board ticket keys/titles/states, so it is a GLOBAL read. Soft-deleted tickets (`deleted_at`) filtered out. No migration (`alembic heads` stays `2722c9066c32`). Node/edge field shape is the STABLE contract PH-277 consumes — do not rename post-merge.
- ConceptTag CRUD API + ticket attach/detach + `tag.read`/`tag.manage`/`tag.assign` caps [PH-273] — child 2/7 of epic PH-271; the API/permission/serializer layer ON TOP of the frozen PH-272 data model. New GLOBAL router `app/api/concept_tags.py` (`/api/concept-tags`, registered after `tickets.router`) + service `app/services/concept_tags.py` (CRUD, tag↔tag link create/delete, ticket attach/detach). Permission checks live in the SERVICE layer (mirrors `services/tickets.py`), NOT the router. Three caps: `tag.read` is GLOBAL (every default role) — board-independent reads; `tag.manage` is GLOBAL **admin-gated** (granted ONLY via the admin `*` wildcard, NEVER on a non-admin role list); `tag.assign` is **board-scoped via the ticket's board** (`require_permission(actor, ticket.board, "tag.assign", resource=ticket)`). Because a global ConceptTag has no board and there is no global-admin concept (admin is always a per-board `BoardMembership.role`), the new `core/permissions.py:require_global_permission(actor, required, memberships_with_boards)` helper gates the board-less caps with "admin on ANY board" semantics — the caller loads the actor's memberships WITH boards' roles eager-loaded (`current_actor` only selectinloads `Actor.memberships`, not the board) and passes `(role, board)` pairs in, keeping the gate self-contained + async-safe without broadening `current_actor`. **Attach is idempotent-success (200, not 409)**: pre-check the junction → return the current ticket on a re-attach (no duplicate row, the `uq_ticket_concept_tag` invariant holds); detach of a non-attached tag is a symmetric 200 no-op (PH-276 chip toggles never special-case a non-error); an `IntegrityError` on a concurrent race is swallowed as the same idempotent path. `TicketResponse.concept_tags` is a SEPARATE field (`list[{id,slug,name,color}]`) — NEVER overloads `labels: list[str]`. Tag↔tag links: ConceptTag has no link back-ref collection yet (PH-272 deferred to PH-275), so a tag's edges are assembled with a SEPARATE `select(ConceptTagLink).where(source==id OR target==id)`, each row `selectinload`-ing both endpoints (N+1-free). App-layer guards added here (deferred from PH-272): self-loop → 422 `InvalidConceptLink`, duplicate `(source,target)` → 409 `Conflict` (reverse pair stays distinct); transitive cycle detection is PH-275's seam, NOT built here. No migration (`alembic heads` stays `2722c9066c32`). **Operator follow-up**: the new caps land in `DEFAULT_WEB_ROLES` but bootstrap is NOT idempotent — `docker compose exec backend python -m app.cli update_board_roles` must be run to propagate them to existing live boards (deferred to post-merge per the integration-branch no-live-DB-mutation rule).
- ConceptTag global model + TicketConceptTag junction + directed ConceptTagLink (self-M2M, explicit foreign_keys) + additive migration down_revision=b1468dc15870 [PH-272] — FOUNDATION child of epic PH-271 (concept-graph); data layer ONLY (API/permissions/serializers are PH-273). `ConceptTag` is GLOBAL (NO `board_id`, cross-board sharing is the point of the epic) with a named `UniqueConstraint(slug)` for stable/portable downgrade. `ConceptTagLink` is **DIRECTED** (`source_tag_id`→`target_tag_id` + nullable `relation` ∈ relates|parent|depends): directed is the only shape carrying both asymmetric (parent/depends) and symmetric (relates) semantics; the graph layer (PH-275) collapses to undirected when `relation` is symmetric. `uq_concept_tag_link_source_target` dedupes ONE direction — the reverse `(target, source)` is a DISTINCT row by design (lets `A parent B` and `B depends A` coexist). Both self-FK relationships MUST set explicit `foreign_keys=[source_tag_id]`/`[target_tag_id]` or mapper config raises `AmbiguousForeignKeysError`. Self-loop/cycle guards are app-layer (PH-273), NOT enforced at the DB. Migration `2722c9066c32` (down_revision `b1468dc15870`) is STRICTLY ADDITIVE — three plain `op.create_table` (no batch, no ALTER on existing tables, SQLite-safe), reverse-order downgrade; spurious autogen `alter_column`/`drop_index` noise on git_commits/sonarqube_metrics/repositories deliberately stripped. **ASYNC-SAFE note for PH-273 consumers**: `Ticket.concept_tag_links` is a lazy collection — any async read MUST `selectinload(Ticket.concept_tag_links).selectinload(TicketConceptTag.concept_tag)` or async lazy-load raises `MissingGreenlet`.
- per-repo SonarQube model: `Repository.sonarqube_project_key`, `SonarQubeMetric (board_id, repo_id)`, `SonarScanJob.repo_id` [PH-246] — the data-model foundation for per-repo Sonar (full scan/health behavior on [[components/sonarqube]]). `Repository` gains `sonarqube_project_key` (String(400), nullable) — the per-repo scan source of truth (primary repo backfilled from the board's legacy key, siblings derive lazily). `SonarQubeMetric` gains `repo_id` (FK `repositories.id`, nullable, CASCADE) and its unique constraint relaxes `uq_sonarqube_metric_board (board_id)` → `uq_sonarqube_metric_board_repo (board_id, repo_id)` — was 1 board:0..1, now 1 board:N (one upsert-latest row per repo); the `Board.sonarqube_metric` 1:1 relationship is renamed to `sonarqube_metrics` 1:N with a new `Board.primary_sonarqube_metric` back-compat accessor (so `BoardResponse.health` stays the primary repo's metric). `SonarScanJob` gains `repo_id` (FK, nullable, CASCADE) + `repo_slug` snapshot (one job per scannable repo, idempotent per `(board_id, repo_id)`). `Board.sonarqube_project_key` is KEPT (legacy fallback + PH self-scan identity), NOT dropped. Migration `b1468dc15870` is ADDITIVE-ONLY + backfilled + SQLite-safe (`batch_alter_table` for the FKs + constraint relax — SQLite has no ALTER-ADD/DROP-CONSTRAINT); backfills the primary repo's key from the board column (no rename) + metric/job repo_id from the board's primary repo, so KIM/PH/GXA keep their exact project_key + health. `get_board`/`list_boards` now `selectinload(Board.sonarqube_metrics).selectinload(SonarQubeMetric.repository)`.

## Known gotchas

- Re-fetching a ticket in the SAME session after mutating its relationship returns the STALE collection [PH-273] — the test/service sessions use `expire_on_commit=False`, so a `Ticket` already in the identity map keeps its already-loaded `concept_tag_links` collection across a commit. After `attach_concept_tag`/`detach_concept_tag` inserts/deletes a `TicketConceptTag` row, a fresh `get_ticket(...)` query returns the cached instance with the STALE (empty) collection → `concept_tags` serializes empty even though the row is in the DB. Fix: `session.expire(ticket, ["concept_tag_links"])` after the commit so the re-fetch's `selectinload` reloads it. (In production each request is a fresh session, so this only bites same-session flows — service round-trips + tests — but the expire makes it correct everywhere.)
- Every ticket read MUST eager-load `concept_tag_links` → `concept_tag` or `ticket_response` raises MissingGreenlet [PH-273] — `_ticket_load_options()` in `services/tickets.py` (the SHARED load path for get/list/create/update/assign/claim) was extended with `selectinload(Ticket.concept_tag_links).selectinload(TicketConceptTag.concept_tag)`. Any NEW ticket-read query that bypasses `_ticket_load_options()` and then serializes via `ticket_response` (which walks `ticket.concept_tag_links[*].concept_tag`) will blow up under async — route reads through `get_ticket`/`query_tickets`, don't hand-roll a ticket select.
- `ConceptTagLink` is a bare junction with NO `TimestampMixin` [PH-273] — unlike `ConceptTag`, it has no `created_at`/`updated_at`. Order edge lists by `id` (stable), not `created_at`.
- Graph node ids are TYPE-PREFIXED strings, never bare UUIDs [PH-274] — `/api/graph` nodes use `ticket:<uuid>` / `tag:<uuid>`; edge `source`/`target` reference those prefixed ids verbatim. A raw-UUID scheme would let a ticket node and a tag node collide in the id namespace. PH-277 (frontend /space) resolves an endpoint to its node by exact string match and relies on the `type` discriminator + the bipartite invariant (`has_tag` connects ticket↔tag, `tag_link` tag↔tag, `epic` ticket↔ticket) — keep these stable. To stay N+1-free, NEVER lazy-access `.board`/`.concept_tag`/`.source_tag`/`.target_tag` outside the eager-loaded set; the assembly is pure in-memory after the 3 selectinload queries.
- Mutating a JSON column in place may not persist [PH-168] — `Workflow.transitions` is a JSON column. Editing a nested list/dict element in place (e.g. `transition["allowed_roles"] = [...]`) is not seen by SQLAlchemy's default change tracking, so the UPDATE never fires. `repair_workflow` sidesteps this by **reassigning a brand-new list** (`workflow.transitions = new_transitions`) *and* calling `flag_modified(workflow, "transitions")`. Any future workflow-JSON edit must do the same or the write is silently dropped.
